THE CLAIMS AUDITThe EXL3 recipe ships pinned to exactly one window (262,144) — conservative. The community "500K KV" claim turned out to be the 2048-block configuration: real, measured here at 524,288, full speed. Removing the pin entirely: 804,864 tokens, then validated the hard way — probes, a 254K needle retrieval, and three simultaneous 250K requests with zero preemption events in the server log. The pin is caution, not necessity. (Sero's 422K pool claim measured 359K on our rig — ordinary cross-host VRAM accounting drift, not inflation. Both authors' claims survived audit within honest tolerances.)
WHY 4-BIT KV ISN'T A QUALITY TRADE HEREQuantizing the KV cache perturbs what the model remembers about every token it has read — the obvious fear is fuzzy recall at depth. Measured: the 4-bit body posts the BEST deep-context scores on this instrument and exact needle retrieval at 254K. GLM's MLA architecture stores a compact latent per token, and the nvfp4_ds_mla format block-scales it specifically; at least for this model family, half the memory per token costs nothing we can detect. The sibling investigation (qwen, 8-bit vs 16-bit KV) reached the same verdict one rung up the ladder — and there, 16-bit could not even SERVE 128K on the card that 8-bit serves it flat.

All pools read from vLLM boot logs (kv_cache_utils GPU KV cache size) on 4× RTX PRO 6000 Blackwell 96 GB. Stress method: vllm bench serve, 3 prompts × ~250K random tokens, max-concurrency 3, 128-token outputs; server log audited for preempt/abort/OOM after the run (0 hits). Deep-concurrency under-provisioned pools measured separately (100K × c=1/2/3 on the hybrid: per-stream 48.2 → 8.1 → 3.2 tok/s).
