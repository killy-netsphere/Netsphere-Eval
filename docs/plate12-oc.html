Memory, Not Cores

I overclocked four Blackwell cards looking for decode throughput. The core offset wasn't where it lived — memory bandwidth was, and the deeper the context, the more it paid.

The split is exactly what the workload predicts. Decode is memory-bandwidth bound — one token at a time, weights streamed from VRAM every step, arithmetic intensity near zero. Prefill is compute bound — thousands of tokens batched into dense matmuls that saturate the SMs. Each clock helps the phase it governs, and neither does anything measurable for the other.

+400 is no better than +200. The prefill gain saturates immediately and then flattens, so the extra core headroom buys nothing while sitting closer to the +700 symptom threshold. On this evidence the locked +350 is generous; +200 would deliver the same 2% with more margin.

THE WALL

FAILURE MODE · GPC +1000

It didn't corrupt. It went silent.

I walked the core offset up in steps. +700 produced the first symptom: a sweep that returned no output at all. +1000 wedged the driver outright — nvidia-smi entered uninterruptible D-state, the TP=4 NCCL collective deadlocked across all four GPUs, the host stopped accepting SSH, and recovery required a power cycle.

ECC stayed 0/0 through every arm, including the one that killed the host. I had tripwires on ECC counters and on output determinism. I had none on absence of expected output — which is the signal that actually fired first. Offsets don't survive a reboot, so the failure self-cleared; that is luck, not design.

WHAT I LOCKED

  • Memory +6000 · core +350. Memory sits at 16,365 MHz, roughly +22% bandwidth. Core is held well inside the +700 symptom threshold.
  • Thermals are not the constraint. 42–50°C across a two-hour pegged-GPU soak under water. The limit I hit was driver stability, not heat — which is why "it runs cool" is not evidence that an offset is safe.
  • The overclock is worth ~7%. Speculative decoding is worth 170%. The same sweep measured MTP-3 against no-MTP at identical clocks: 34.4 → 91.5 tok/s. Every clock I touched is a rounding error next to the serving config, and I spent a host reboot learning it.

Measured on one host: 4× RTX PRO 6000 Blackwell, TP4/DCP4, GLM-5.2 EXL3 TR3-3.0bpw, gpu-memory-utilization 0.96, fp8 KV. Offsets applied through the NVML pstate-aware clock-offset API, not nvidia-smi -lgc/-lmc — both of those were measured inert on this box, since the cards run in P1 under inference load and the pinned bins are P0-only. Three runs per rung per arm; means plotted, no smoothing. Decode measurements on this rig carry roughly ±5% run-to-run variance, which is why the memory result is reported and small differences are not.
